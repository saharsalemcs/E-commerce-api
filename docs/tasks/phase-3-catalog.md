# Phase 3: Catalog

Goal of the phase: categories, products, and variants where each size/color combination is its own SKU with its own stock; controlled inventory adjustments; and public discovery (filter, sort, paginate, search, detail by slug).

Roles in this phase: catalog writes are allowed to `admin` and `catalog_manager`. Public reads show only active items.

---

### P3-T01 Categories

**Goal:** Staff manage categories; the public sees active ones.
**Source:** EC-01.
**Depends on:** P2-T10.

**Scope**
- Endpoints:
  - `GET /api/v1/categories` (public): active categories, paginated.
  - `GET /api/v1/categories/:slug` (public): one active category.
  - `POST /api/v1/admin/categories`, `PATCH /api/v1/admin/categories/:id` (admin, catalog manager).
  - `DELETE /api/v1/admin/categories/:id` (admin, catalog manager). Decide: hard delete or deactivate. P3-T02 adds a rule that a category with products cannot be hard-deleted.
- Data: name (unique, case-insensitive), slug (unique, generated from name with `slugify`), description (optional), active flag, timestamps.
- Business rules: slug is generated by the server, never sent by the client; renaming decides whether the slug changes (think about old links and choose).

**Not in this task:** subcategories (Phase 8).

**Acceptance criteria (verify in Postman)**
- Create "Men Shoes" -> slug `men-shoes`. Same name again (any case) -> `409`.
- Deactivated category -> not in the public list, public `GET` by slug -> `404`.
- Admin write endpoints: no token -> `401`; customer or order operator -> `403`.
- Unknown category id on `PATCH`/`DELETE` -> `404`.

**Concepts to review:** slugs and stable URLs; case-insensitive uniqueness (collation or a normalized field).

**Definition of done:** all acceptance criteria pass in Postman, unauthorized access is rejected, invalid input is rejected, database state is correct, and `/review-task` has returned "Ready".

### P3-T02 Product and variant model, create product

**Goal:** Implement the Product and Variant models from your ERD (variants are a separate collection, one document per SKU) and let staff create a product with its first variants.
**Source:** EC-01; EC-02; brief section 06 (Product / ProductVariant).
**Depends on:** P3-T01.

**Scope**
- Endpoint: `POST /api/v1/admin/products` (admin, catalog manager). Body: title, description, category id, images (array of URL strings), attributes you want to show (optional), and one or more variants.
- Product data: title, slug (unique, server-generated), description, category ref, images (validated URLs, a maximum count), active flag, timestamps.
- Variant data: SKU (unique across **all** products, normalized case), size, color (either may be optional for single-variant products), price (integer piasters, > 0), stock (integer, >= 0, **set by the server to `0` on creation**), active flag.
- Business rules: no two variants of the same product have the same size+color; the category must exist and be active; stock cannot be negative (enforce in the schema, not only in Zod); `stock` in the request body is rejected, because the first stock comes only from an inventory adjustment with reason `initial_stock` (P3-T05).
- Add the rule from P3-T01: a category with products cannot be hard-deleted -> `409`.
- Audit: product creation writes an entry (initial prices).

**Not in this task:** editing products or variants, any stock change (P3-T05).

**Invariants that apply:** each purchasable size/color is a unique SKU with its own stock (EC-02); stock never negative.

**Acceptance criteria (verify in Postman)**
- Product with 2 variants (same shoe, size 42 and 43) -> `201`, two separate SKUs, both with stock `0`.
- Body with `stock` on a variant -> `400`.
- Duplicate SKU (even on another product, or different case) -> `409`.
- Two variants with the same size+color -> `400` or `409`.
- Price `99.5` or `-1`, invalid image URL -> `400`.
- Category id that does not exist -> `404` (or `400`, documented).
- Delete a category that has a product -> `409`.
- No token -> `401`. Customer or order operator -> `403`.

**Concepts to review:** unique indexes across separate documents (decided in P1-T08: variants are their own collection, see `docs/design/data-model.md` section 3.1); integer money.

**Definition of done:** all acceptance criteria pass in Postman, unauthorized access is rejected, invalid input is rejected, database state is correct, and `/review-task` has returned "Ready".

### P3-T04 Variant management

**Source:** EC-02; brief section 02 (log financial changes).
**Depends on:** P3-T02.

- Business rules: a new variant starts with stock `0`; SKU is immutable once created (decide and justify, think about order snapshots and reports); `stock` in either body is rejected (stock only changes through inventory adjustments or orders); a variant belongs to the product in the path (wrong pair -> `404`); the size+color uniqueness rule still holds.

### P3-T05 Inventory adjustments (including initial stock)

**Goal:** Catalog managers change stock in a controlled, atomic, audited way, with a reason. This is also the only way a new variant gets its first stock.
**Source:** Brief section 02 (catalog manager: "controlled inventory adjustments"); EC-02; decisions "Inventory", "Stock".
**Depends on:** P3-T04.

**Scope**
- Endpoint: `POST /api/v1/admin/variants/:variantId/stock-adjustments` (admin, catalog manager). Body: a signed integer change (for example `+20` or `-2`), a reason from a fixed list (`initial_stock`, restock, damaged, lost, correction), an optional note.
- Business rules: the update is a **single atomic conditional operation**: it fails if the result would be negative; no read-then-write. Zero change is rejected. The response includes the new stock.
- `initial_stock`: a positive change only, allowed only when the variant has no previous adjustment; a second `initial_stock` on the same variant -> `409`. Decided in P1-T08: the variant has an `initialStockSet` flag, flipped from `false` to `true` in the **same conditional atomic update** that adds the stock (no read-then-write, so two simultaneous requests cannot both succeed).
- Audit: every adjustment writes an entry with the change, reason, before/after stock, actor. Decided in P1-T08: there is no separate InventoryAdjustment collection; the audit entry (`inventory.adjusted`) is the adjustment record.

**Not in this task:** stock changes from orders (Phase 5).

**Invariants that apply:** stock never negative; no order may take more than available stock (this task builds the same atomic pattern orders will use).

**Acceptance criteria (verify in Postman)**
- New variant (stock 0), `+20 initial_stock` -> `200`, stock 20, audit entry with reason `initial_stock`.
- Second `initial_stock` on the same variant -> `409`, stock unchanged. `initial_stock` with a negative change -> `400`.
- Stock 5, change `-2` -> `200`, stock 3, audit entry present.
- Stock 3, change `-10` -> `409`, stock still 3, no audit entry.
- Missing reason, reason not in the list, change `0`, change `1.5` -> `400`.
- Unknown variant id -> `404`.
- No token -> `401`. Order operator or customer -> `403`.

**Concepts to review:** atomic conditional updates (`$inc` with a filter on the current value); race conditions in read-modify-write; why the DB, not JavaScript, must enforce this.

**Definition of done:** all acceptance criteria pass in Postman, unauthorized access is rejected, invalid input is rejected, database state is correct, and `/review-task` has returned "Ready".

### P3-T06 Public product listing: filter, sort, paginate

**Goal:** Shoppers browse active products with category filtering, price range, sorting, and pagination.
**Source:** EC-03.
**Depends on:** P3-T04.

**Scope**
- Endpoint: `GET /api/v1/products` (public).
- Query: `category` (slug), `minPrice`, `maxPrice` (piasters), `inStock` (boolean), `sort` (from an allow-list, for example price ascending/descending, newest), `page`, `limit`.
- Business rules: only active products in active categories, considering only active variants; each item shows the information a list card needs (title, slug, first image, price or price range, in-stock flag). Unknown sort values are rejected, not ignored.
- Price lives on variants, so "sort by price" and "filter by price" need a decision: compute at query time (aggregation) or keep a denormalized min/max price on the product that is updated whenever variant prices change. Choose and justify.
- Express 5 uses the "simple" query parser by default, so nested syntax like `price[gte]` is not parsed into an object. Design flat query params, or change the parser on purpose and explain why.

**Not in this task:** text search (next task).

**Acceptance criteria (verify in Postman)**
- Filter by category slug -> only that category's active products.
- `minPrice`/`maxPrice` -> correct results; `minPrice > maxPrice` -> `400`.
- `sort=price` vs `sort=-price` (or your names) -> correct order. `sort=password` -> `400`.
- A deactivated product or one in a deactivated category never appears.
- Pagination meta follows the P2-T05 convention.

**Concepts to review:** MongoDB query filters and sort with indexes; compound indexes for filter+sort; denormalization trade-offs; Express 5 query parser setting.

**Definition of done:** all acceptance criteria pass in Postman, invalid input is rejected, and `/review-task` has returned "Ready".

### P3-T07 Product search

**Goal:** Shoppers search products by text, combined with the filters and pagination from P3-T06.
**Source:** EC-03 ("search").
**Depends on:** P3-T06.

**Scope**
- Query: `q` on `GET /api/v1/products`.
- Decide: MongoDB text index (ranking, language stemming, whole-word matching) or a case-insensitive regex on title (partial matches, but slow without an anchored prefix and unsafe if input is not escaped). Compare both and choose. Record the choice in `docs/02-decisions.md`.
- Business rules: `q` combines with the other filters; the maximum `q` length is limited; special characters cannot break the query.
- Optional: a "relevance" sort when `q` is present.

**Not in this task:** semantic search (out of scope).

**Acceptance criteria (verify in Postman)**
- `q=shoe` returns matching products; with `category` it narrows.
- `q=.*` or `q=(` does not crash and does not match everything by accident.
- Very long `q` -> `400`.

**Concepts to review:** MongoDB `$text` and text indexes; regex injection and ReDoS; escaping user input.

**Definition of done:** all acceptance criteria pass in Postman, invalid input is rejected, and `/review-task` has returned "Ready".
