## 2026-11-28: P2-T03 Login and authentication middleware
- **How it was done:** the learner wrote the first version of the login service, controller, route, validation schema, token verification and authentication middleware, then fixed the inverted password check, `return` vs `throw`, the missing-header crash and `throw next(...)` after review. The mentor wrote on request: the password-changed check, the JWT error mapping, the dummy-hash comparison, the move of the middleware into `modules/auth`, `GET /users/me` (route and controller) and the decision records. The learner verified the task in Postman.
- **Feedback:** the first login condition rejected the correct password and accepted a wrong one, so any known email could get a token: test the case that must fail, not only the happy path; an `AppError` that is returned instead of thrown becomes a successful `200`; `throw next(err)` reports the error twice, so use one of the two; a missing `Authorization` header must give `401`, not crash with `500`; library errors (JWT) need mapping in the error middleware or they become `500`; `iat` is in seconds while a `Date` is in milliseconds; wrong email and wrong password share one message and one bcrypt cost; the authentication middleware lives in `modules/auth` because `common` should not depend on a module. Recorded in `docs/decisions/phase-2.md`.
- **Open (not blocking):** `JWT_SECRET` still accepts an empty string; the login password has no maximum length (bcrypt ignores bytes after 72); the email schema is repeated in register and login.
- **Concepts:** user enumeration and timing attacks, `throw` vs `return` in async functions, Express 5 forwarding of rejected promises, JWT error classes (expired vs invalid), `iat` vs password-changed timestamp, negative testing, dependency direction between shared code and modules.
